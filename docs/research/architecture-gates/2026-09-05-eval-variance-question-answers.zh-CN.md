## 这不是什么

这不是在说已实现的机制不可靠。调研已经说过，而且仍然成立：分布、极差、政策下拒绝 `repetitionCount: 1`、按身份摘要分组、运行路径不能写回的钉住基线、在分布之间而不是在单个分数之间计算的配对差值，都该留下。可能变的是形状和谁来用，不是算术是否可信。

这也不是实现卡住。四个 PR 有 mutation 证据。停下来的原因是：先实现后调研，然后发现没有任何入库 EvalSet 能走到新代码——这是设计冻结。

## 一句话

调研的诊断是对的。推荐的落地范围过大。

长期形状：永远公布分布；以后可以在上面叠一个具名决策规则；任何归约都不能替换原始计数。这比「禁止给出任何具名答案」更干净，也是把 inspect_ai 默认值倒过来的正确方式。

本轮：不要建归约器目录；不要把方差政策接到确定性车道上；不要保留一个把结构性事实和未校准阈值混在一起的 `Trustworthy` 布尔值。拆开闸门，给报告加上廉价的可靠性派生字段，明说这套机制是**休眠**装船、本轮没有消费者，四个 PR 就地修订，而不是重塑。

## 四个问题所依据的行业实践

2026-09-05 调研门的对照集（inspect_ai、terminal-bench、evals、vitest-evals、Maka）对本仓库 `.reference/` 里的检出是对的。四个问题还有一层该门当时不必结算、而随后推荐权重不够的更宽行业形状。

### 原始次数普遍留下；合成是之后的、具名的一步

- inspect_ai 用一个 `Epochs(epochs, reducer)` 对象把次数和合成规则绑在一起。每个 epoch 的分数留在日志里。默认 reducer 是 `mean`。`collect` 保留每一个值。可以同时点名多个 reducer，`headline_metric` 记录哪个归约后的数字是头条（[Scoring Metrics](https://inspect.aisi.org.uk/metrics.html)）。
- terminal-bench 每个 trial 都落盘，汇总时公布 2 的幂上的 `pass@k` 曲线。
- Maka 把 `repetitions` 展开成 cell，然后什么都不聚合。这是本项目**没有**方差机制时最像的对照。
- HumanEval / HuggingFace `code_eval` 留下全部 `n` 个样本，事后估计 `pass@k`（Chen et al., 2021, [arXiv:2107.03374](https://arxiv.org/abs/2107.03374)）。

没有成熟框架把「保留分布」写成禁止具名答案。它们让合成规则显式。inspect_ai 的 `collect` 就是本项目当成强制的行为，只是做成九选一。共享的价值观是「规则不能藏起来」。表达不同：他们提供选择，这份设计写成了禁令。

### 随机 agent 评测报的是曲线，不是校准过的闸门

- Chen 2021 的 `pass@k` 是 k 次里至少一次成功的概率，在 `n ≥ k`、其中 `c` 次通过时用无偏估计 \(1 - C(n-c,k)/C(n,k)\)。
- terminal-bench 对「这次测量稳不稳」的回答就是 `pass@k` 曲线本身。读它不需要阈值。
- τ-bench（Yao et al., 2024, [arXiv:2406.12045](https://arxiv.org/abs/2406.12045)）报的是 **pass^k**：连续 `k` 次独立试验**全部**成功的概率。这个数字随 `k` 增大而下降。它是可靠性指标，比 `pass@k` 更贴近本项目的章程。
- inspect_ai 两套都给：`pass_at(k)` 是 Chen 估计器；`pass_k` / `at_least(k)` 是「k 次全过」/「至少 k 次过」。
- *On Randomness in Agentic Evals*（2026）发现即使 temperature=0，单次 `pass@1` 也能差 2–6 个百分点，并建议同时报乐观包络和悲观包络。

Cell 级「这 k 次里有没有一次通过」是 `at_least(1)`，不是 Chen 的 `pass@k`。`pass@k` 通常是数据集级的「多大比例的题在 k 次里被解开」。本项目 nightly 车道能负担的样本量（个位数，常常是 2）下，无偏估计和原始 `c/n` 几乎是同一件事。真正有意义的套件级曲线，等有套件再画。

### 不确定性是披露；未校准阈值不是闸门

inspect_ai、EleutherAI `lm-eval-harness`、HELM 报的是 `mean ± stderr` 或 bootstrap 区间。相关测量用 **clustered** 标准误，这正是 inspect_ai 在样本非 IID 时去用它的原因。Miller（2024）是同一条规则。没有一家因为格内散度超过一个没人测过的数字，就拒绝公布分数。

调研门在五个框架里搜 `untrustworthy` / `unreliable` / `too_variable` / `insufficient_samples` 没有对口命中，这件事仍然成立。最接近的工业对应物是另一类机制：

- 统计：`n` 不足、A/B 报 inconclusive；
- inspect_ai：全部被过滤时返回 `NaN`，比他们自己四处「一个样本 `stderr = 0`」更诚实；
- CI：flaky test 隔离。

拒绝从一个样本报 `stderr = 0`，是这份设计比 inspect_ai 更严、而且应该留下的地方。把一个未校准的数值上限塞进同一个布尔值，不是同一件事。

### 确定性车道的重复是 flake 检测，不是方差政策

Bazel `--runs_per_test` 加 `--runs_per_test_detects_flakes` 得到的状态是 **FLAKY**，不是质量信号判断
（[Command-line reference](https://bazel.build/reference/command-line-reference)）。
Go `-count=N` 是同一件事。Uber 的预提交 flake 检测也是 `runs_per_test`。规则就是「跑两次，结果必须一致」。它不需要 `maxNumericSpread`、`minVerdictStability`、基线文档或配对差值。

方差设计自己的开放问题 3 已经写过：fixture 车道上 `spread > 0` 是确定性缺陷，折进方差政策会模糊整份文档的区分。#173 接受设计时把这个问题标成开放且不进范围。

## 问题一 — 禁止合成 vs. 具名归约器

随后推荐里的合成方案——永远公布分布，旁边允许一个具名归约——长期形状是对的。它比 inspect_ai 更干净：inspect_ai 默认 `mean`，调用方不加点 `collect` 就会把 4/5 抹掉。本项目应该把这个默认倒过来。

本轮不该实现它。

| | 保持禁止合成 | 本轮就做 inspect_ai 式目录 | 永远公布分布，以后再加具名决策规则 |
| --- | --- | --- | --- |
| 留下 | 产物形状唯一，好测 | 合成规则进入冻结、可摘要的文档 | 原始计数藏不住；需要 yes/no 的消费方拿到一条具名规则 |
| 代价 | 每个消费方各自发明规则，比「具名」更不透明 | 下周就会有人要 `mean`；今天没有消费方需要目录 | 多一个字段，可以先空着 |

**决定：** 长期形状写进设计。本切片不加 `distribution` / `at_least(k)` / `pass_at(k)` 作为归约器。

理由，按约束顺序：

1. 章程要的是规则显式，不是框架拒绝给答案。这是两句话。
2. 现在没有任何车道在问「这格算通过吗」。父评测设计规定 live 质量信号在四个 GA blocker 都有独立证据之前都是 advisory，并且禁止用质量信号卡住普通 PR CI。没有消费者的具名决策规则，就是调研刚抓住的「建好没人用」，换了个名字。
3. `mean` 和 `median` 继续拒绝。这条拒绝针对的是不抹掉 4/5，对照之后仍然成立。`at_least(k)` 和 `pass_at(k)` 等第一个需要 yes/no 的消费者再加。
4. 不要叫 reducer。inspect_ai 的 reducer **替换** epoch 视图，指标再作用在归约之后。本项目的具名答案应该是**决策规则**：作用在已公布的分布上，永远不删原始计数。这样「永远公布分布」在第一条具名答案落地之后仍然为真。

## 问题二 — 要不要 `pass@k`

加，只当指标不当闸门。随后推荐的这一半是对的。两处要收紧。

第一，Cell 级「k 次里至少一次通过」是 `at_least(1)`，不是 `pass_at(k)`。inspect_ai 的 `pass_at(k)` 是 Chen 估计器。名字混了，第一次拿去和公开基准比就会不诚实。

第二，对一个在评自己可靠性的 harness，**pass^k**（k 次全过）才是更承重的数字。`pass@k` 是能力上界；pass^k 是无人值守时能不能信。τ-bench 引入 pass^k 就是为这个。本项目的章程更接近 τ-bench，而不是排行榜。

**决定：** 现有 distribution block 上的派生字段，不是归约器，也不是闸门。

1. Cell 级只报计数已经能直接读出的东西：可评估、通过、失败、不确定。`N = 2` 时，「有一次过」和「两次都过」就是 pass@1 和 pass^2。在 `N` 大到无偏估计会和 `c/n` 分家之前，不值得单独实现 Chen 估计器。
2. 套件级 `pass@k` 曲线才是 terminal-bench 的形状。入库套件现在太小，那条曲线没有意义。本轮不画。
3. 这些字段属于 Task 7 的报告块。它们不依赖归约器概念。

「可选」不是「忙就可以不做」。它是整份提案里唯一不需要校准阈值就能读的信号，而这正是一份自认未校准的首份政策该抓住的东西。「可选」的意思是：它不是闸门，也不是重塑四个 PR 的理由。

## 问题三 — 「不可信」闸门

把结构性事实和阈值判断拆开是对的。拆完还留一个 `Trustworthy bool` 是错的。消费方会看布尔值、忽略理由文本。#175 里「五次里一个幸存者被报成完美可信」就是这样发生的：两种不同的陈述共享一个标签。

「全场没人有这个闸门」应该写在决定旁边。它改变的是阈值那一半，不是结构性那一半。

| 种类 | 例子 | 行业对应 | 本轮 |
| --- | --- | --- | --- |
| 结构性事实 | 5 次里 1 次可评估；全是 indeterminate | `n` 不足；inspect_ai 的 `NaN`；A/B 的 inconclusive | 硬报告规则：这格不能报成 pass。这就是拒绝 `stderr = 0`，不是创新 |
| 阈值判断 | 散度 0.33 超过声明的 0.20 | 没有对标；数字未校准 | 参考性元数据，继承政策自己的 `uncalibrated` 标记。在被引用的运行产出这些上限之前，不得把一格从 pass 改写成「不算过」 |

**决定：** 两个字段，不要一个布尔值。

```text
evaluableEnough        # 结构性。假 ⇒ 不得报成 pass
exceedsDeclaredLimits  # 阈值比较，带着校准状态
```

「在框架里独一无二」写在 `exceedsDeclaredLimits` 旁边，并把章程比跑分工具更保守这一点写成它存在的理由。不要写在 `evaluableEnough` 旁边。

## 问题四 — 第一个消费者

这才是真正的产品问题。随后推荐的第三条路解错了题。

两边的绑是真的：给确定性车道加重复便宜，但证明不了机制有价值；等第一次真实模型运行，在这台没有凭证的机器上机制会闲置。「给确定性车道加重复，但当作散度必须恰好为 0 的确定性检查」是一个好的**确定性**检查，是一个坏的**方差政策**第一消费者。

| 路径 | 证明什么 | 代价 |
| --- | --- | --- |
| A. 确定性车道 `N = 2` 当方差消费者 | 管道通了 | 按定义散度就是 0，阈值、4/5、未校准披露全部打不中。开放问题 3 禁止这条路。scheduled Context 全矩阵刚从 PR 路径拆出去（#157），因为它在那里已经太贵 |
| B. 等第一次 live 运行 | 方差本来就是 live 车道的概念 | 没凭证就闲置 |
| C. 确定性车道 `N = 2`，「散度必须为 0」，走方差政策 | harness 自身不确定是 bug | 用错了工具。那种检查不需要方差政策文档、基线、配对差值或可信布尔值 |

**决定：** 这套机制本轮没有消费者，以**休眠**状态装船。确定性检查是以后的独立任务，只开在最便宜的 smoke 上。方差政策的第一个消费者是第一个 live EvalSet。

1. 16 个入库 EvalSet 都声明 `repetitionCount: 1`，没有一个在主张方差信号。#177 的 fail-closed 规则已经拒绝「引用了政策却只跑一次」的套件。这是按设计在工作，不是缺一份配置。
2. 把 mutation 测试称作「本轮的消费者」是改名，不是回答。mutation 测试证明的是计算正确，它不是宪章第 92 行（禁止预先实现尚无真实消费者的扩展点）所要求的那种消费者。诚实的说法是：这套机制**休眠**装船——测试过、作为库合进去、在第一个 live EvalSet 出现之前没有任何入库配置能走到它。设计里必须把这句话明写出来。先合进一个测试过的库、第一份配置还没到，是平常事；声称它已经有消费者了，不是。
3. 如果要确定性检查，那是 Bazel `runs_per_test`，不是 `och.eval.variance-policy`。候选：只在最便宜的 smoke 套件（不是 scheduled Context 全矩阵）上设 `repetitionCount: 2`，规则是「两次 Outcome 和 Score 必须逐项相同，否则失败」。那是以后的任务，也是另一份文档。
4. 第一份该引用方差政策的配置，是第一个 live 质量 EvalSet。在那之前不要发明 nightly `N = 5`。

**为什么散度当不了那个确定性检查的信号。** `NumericScore` 只在三处被赋值——`internal/harness/eval/judge.go:233`、`judge.go:240`、`judge_attempt.go:159`——三处全是 judge 路径。确定性打分器从不产生数字分。所以在 fixture 车道上 `NumericScores` 是空的，`NumericSpread` 按构造恒为 `0`，「散度必须恰好为 0」这条规则无条件通过，什么也证明不了。这给上表路径 C 补了第二个独立的否决理由：不只是用错工具，而是一个空检查。它同时也否掉了那张表之后提出的修正版——「判定稳定性必须恰好为 1」——那个版本换对了信号，却仍然拿方差政策当载体。确定性检查必须逐项比对两次的 Outcome 和 Score，也就是第 3 点里那个候选方案已经写明的做法。

## 共识核对表

每一行都是是/否。六行都「是」，就够修订设计并落地 PR。任何一行「否」都是另一次修订，应写明是哪一行、改成什么。

1. 长期形状是「永远公布分布；以后可以在上面加具名决策规则；mean/median 继续拒绝。」
2. 本轮不加具名归约器目录。
3. 报告增加廉价的可靠性派生字段（`c/n`，以及 `N ≥ 2` 时 Cell 级「至少一次通过」/「全部通过」的读法）。它们不是闸门。Cell 级「至少一次通过」不叫做 `pass_at(k)`。
4. `Trustworthy bool` 拆成 `evaluableEnough`（硬）和 `exceedsDeclaredLimits`（校准前只作参考）。「全场没人有」写在阈值那一半旁边。
