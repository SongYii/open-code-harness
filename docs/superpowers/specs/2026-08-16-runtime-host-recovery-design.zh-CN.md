# Runtime Host 与崩溃恢复（Slice 4）中文阅读版

**状态：** 草案，待架构门证据

**日期：** 2026-08-16

**父设计：** [生产 Runtime 持久化、恢复与客户端边界](2026-08-13-runtime-persistence-recovery-client-design.md)

**架构门：** `docs/research/architecture-gates/2026-08-16-runtime-host-recovery.md`（证据待补；本规范按父设计第 11 节与 7.8 节冻结切片决策）

**已实现基线：** [SQLite 规范 EventStore](../../architecture/sqlite-eventstore.md)——租约机制、fencing 谓词与 `session_heads` 投影均已交付

## 1. 决策摘要

Slice 4 在已实现的 Application 服务与 SQLite 存储之上构建唯一的
Runtime Host：启动调和、带 fencing 反应的心跳循环、优雅关停，以及
后台审计导出器的生命周期。存储机制已存在；本切片提供宿主策略。

承重切片决策：

1. 包 `internal/harness/runtime` 组合 Application 服务、EventStore 与
   审计导出器。它不拥有任何领域规则，也不新增存储权威。
2. 启动调和完成前命令不可用；审计导出延迟绝不阻塞 Runtime 就绪。
3. 恢复只追加终态事实，`AppendID` 来自固定命名空间的确定性推导，
   绝不重放模型或工具效果。
4. 无法确认租约所有权的宿主停止接纳执行并取消本地工作；被 fence
   的宿主无法追加，因为每个事务都校验其令牌。
5. 无法获取租约的第二个进程以稳定的诊断退出。

## 2. 目标

- 父设计的启动顺序作为一条可审计的序列。
- 恰好一次关闭被打断执行的崩溃调和。
- 有界截止期、失效即停的心跳循环。
- 在界限内取消工作并释放租约的优雅关停。
- 由宿主拥有的导出器生命周期（就绪后启动、关停时停止）。

## 3. 非目标

- 每库多宿主；跨库选主；集群。
- 任何形式的自动模型或工具重试。
- ACP、TUI 或任何客户端面（Slice 5–6）。
- 改动 Slice 2 交付的租约存储机制。

## 4. 启动顺序

严格按父设计 11.2 节序列：

```text
打开数据库 → 校验格式并运行迁移
→ 获取 Runtime 租约与 fencing 令牌
→ 枚举运行中候选
→ ReadStream + 重放每个候选
→ 追加恢复终态事实
→ 开始接受命令
→ 启动后台 JSONL 导出器
```

候选从 `session_heads` 投影（状态 `active`）枚举，且只能由权威流
重放确认——按 Slice 2 合同，投影绝不被当作独立证明。

## 5. 恢复转移

以活动会话、运行中 Turn 与运行中 Assistant Item 结束的权威重放产
出一个原子恢复批次：

```text
assistant.message.interrupted(code = "process_crash", message = "")
turn.interrupted(reason = "process_crash")
```

- 会话保持活动；原 `CommandID` 保持关联血统。
- 恢复 `AppendID` 在固定命名空间内由会话 ID、Turn ID、Item ID 与
  `process_crash` 确定性推导；丢失恢复确认时以完全相同的追加重试并
  解析到原回执。
- 重复调和返回回执或观察既有终态；不能加出第二对终态事实。
- 带运行中 Turn 而无活动 Item 的遗留流只追加同一命名空间加显式
  `no_item` 哨兵的 `turn.interrupted`。
- 活动 Item 引用缺失、终态、不匹配或多个的运行中 Turn 不被修复：
  调和报告 `StoreCorrupt`。
- 不引入长期存在的 `recovering` 领域状态。

## 6. 不自动重放

运行中的事件无法揭示旧进程崩溃发生在发送请求前、流中、provider
完成后、终态提交中、还是提交后确认丢失。自动重复可能重复成本、
回答、文件编辑或远程效果。恢复只关闭不确定的执行；新的用户意图
创建新身份并可记录 `retryOfTurnID` 血统。

## 7. 心跳与 fencing 反应

- 宿主通过存储的 `RenewLease` 按有界间隔心跳，截止期严格短于租约
  期限。
- 确认所有权失败：宿主立即停止接纳新执行、通过 Application 服务
  请求取消在途本地工作、停止导出器。它不删除任何东西，也不尝试
  接管。
- 续约因租约过期失败意味着宿主曾被卡住或挂起；它只能通过正常的
  过期接管路径（令牌递增）重新获取，且仅在在途工作静止之后。
- 时钟异常偏向安全：提前吊销或延迟接管都优于两个活动令牌。

## 8. 关停与第二个宿主

- 优雅关停：停止接纳、取消在途工作并有界等待、在分段边界停止
  导出器，然后在一个事务中通过使租约过期来释放——精确匹配持有的
  runtime ID 与 fencing 令牌，使过期宿主绝不能释放后继者的租约
  （架构门确认的 Pi 规则）。后继接管取下一个令牌。
- 无法获取租约的第二个进程以指名持有者的稳定分类诊断退出；它不
  做调和也不做导出。

## 9. 测试证据

1. 启动调和矩阵：被打断的 assistant item、`no_item` 遗留 turn、
   已恢复流（幂等）、畸形 Item 引用（`StoreCorrupt`）、干净流
   （无操作）。
2. 确定性 `AppendID` 推导与丢失恢复确认后的精确重试。
3. 心跳：续约成功、过期 fencing、停止接纳反应、取消传播到运行中
   执行。
4. 优雅关停顺序与租约释放；后继接管令牌递增。
5. 第二进程诊断。
6. 导出器生命周期：就绪后启动、关停时停止、延迟不阻塞就绪。
7. 尽可能使用确定性时间测试（`testing/synctest`），外加并发 race
   门。

## 10. 交付计划

1. **调和**——候选枚举、重放确认、确定性恢复追加、完整矩阵。
2. **宿主骨架**——启动顺序、接纳门、就绪。
3. **心跳与 fencing 反应**——有界循环、停止接纳、取消传播。
4. **关停、诊断、导出器接线**——释放、第二宿主诊断、导出器启停。
5. **文档与证据**——已实现合同、证据台账、双语、索引更新。

## 11. 排除项

没有多宿主协调；没有模型/工具重放；没有租约机制改动；没有客户端
协议；没有超出 Domain 已定义恢复终态事实的新领域事件。
