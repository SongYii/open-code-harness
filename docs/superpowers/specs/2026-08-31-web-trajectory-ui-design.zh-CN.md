# 网页轨迹 UI 与浏览器传输设计（中文摘要）

**状态：** 已接受（2026-08-31）；本文是与英文规范同步的中文摘要，不是逐字翻译。两者若有分歧，以英文 [2026-08-31-web-trajectory-ui-design.md](2026-08-31-web-trajectory-ui-design.md) 为准。

一个网页轨迹 UI 就是一个 ACP v1 客户端,和 `cmd/acp-client` 完全一样,只是通过 WebSocket 而不是 stdio 触达。这份设计只给"把 ACP 已有的 wire 字节送到浏览器标签页"这件事加一样新东西,别的都不加。

## 核心决策(六条)

1. **新增一个二进制 `cmd/acp-web-bridge`,它是一个哑巴中继,不是第二个 ACP 客户端实现。** 它照搬 `cmd/acp-client` 已有的方式(`-agent`/`-cwd`)拉起 `och -acp`(或任意 ACP v1 agent 二进制),然后只搬字节:子进程 stdout 的一行(去掉换行)变成一个 WebSocket 文本帧;一个收到的 WebSocket 文本帧(补上换行)变成子进程 stdin 的一行。它从不解析 JSON-RPC,不知道任何方法名,也不做轨迹归约。`initialize`、`session/new`/`load`、`session/prompt`、`session/request_permission`、轨迹归约——所有 ACP 语义都在浏览器自己的 TypeScript 里重新实现一遍,那是一个真正独立的 ACP v1 客户端实现,不是 `internal/client/acp`(它没法跑在浏览器里)的薄封装。
2. **桥接进程在同一个 origin 上既提供静态前端、又升级 WebSocket 连接**,所以只有一个 origin、一个端口、每次调用一个进程要处理——没有独立的开发服务器,没有 CORS 的故事要讲。
3. **每一次 WebSocket 升级都要过两道独立的检查**:`Origin` 头(如果存在)必须和桥接进程自己服务的 origin 完全一致(挡住另一个标签页里的恶意 origin 试图连到这个回环端口——调研门里读到的 Codex 自己的 Origin 头规则证明这个威胁是真实的,而且防起来很便宜);以及一个每次启动都随机生成的令牌,和就绪 URL 一起打印到 stderr,以查询参数形式携带(浏览器没法给 WebSocket 握手加自定义头),必须精确匹配(防的是 Origin 挡不住的、共享主机上另一个本地账号)。这一版里绑定地址写死为回环地址,没有开关可以改。
4. **实时渲染这一版原样接受 ACP 的"Never projected on ACP"边界。** 没有 token 用量,没有服务商上报的延迟,没有 `finishReason`——浏览器拿到的和今天任何一个 ACP 客户端拿到的一模一样。但一个粗略、诚实的替代品是免费的:浏览器可以在本地收到每条通知和 RPC 响应时打上本地时间戳,从中推出每个 Turn、每次工具调用的墙钟时长,不需要任何协议改动。这被明确披露为一种近似值(会受网络/渲染抖动影响),绝不冒充服务商上报的延迟。
5. **按 Turn 分组不需要任何新的 wire 字段。** `toolCallId` 本来就是 `turnID + "/" + callID`(`acp-v1.md`),客户端自己知道调用 `session/prompt` 的那一刻就是一个 Turn 的开始,响应返回就是结束;回放时 `user_message_chunk` 标记同样的边界。DeepSeek Harness `ui-trajectory` 那套按 Turn 分组台账的核心思路,完全可以在客户端本地推导出来。
6. **这一版的范围:一个桥接进程、一个子进程、同时最多一个活跃浏览器连接、一个会话。** 没有多标签页扇出,浏览器里没有 `session/list`/`resume`/`delete`,不接转录导出,没有 TLS,绑定地址不可配置。每一条都是有理由的明确排除项(见下),不是漏做。

## 范围之外(这次明确不做,不是漏做)

- **实时 token 用量、延迟、`finishReason`,或者首字延迟/解码耗时拆分的时间轴总览。** 这些字段本来就是 ACP v1 wire 协议刻意不发的。要解决这个矛盾是一个比单个客户端更大的协议级问题,不是这份设计能单方面决定的;转录导出对*已完成*会话确实有这些数据,但把它接进实时浏览器视图是另一个、更晚的阶段。
- **一个会话被多个浏览器同时查看。** 桥接进程只维护一个子进程,同一时刻只中继给一个活跃 WebSocket 连接;新连接会接管上一个连接的接线(让标签页刷新或重连自然work,因为子进程本身没被动过,只是短暂没有读写者),不会同时扇出给好几个标签页,也没有仲裁谁能发输入。真正的多观察者扇出是一个materially 不同、更难的问题(广播加写入仲裁),留给未来需要时再做。
- **浏览器 UI 里的 `session/list`/`session/resume`/`session/delete`。** 这一版的范围和 `cmd/acp-client` 自己的范围完全一致:每次桥接调用一个会话,新建或者用同样的 `-resume <sessionId>` 参数形状恢复。同一个浏览器标签页重连回同一个会话之所以能work,是因为前端自己把会话 id 记在自己的 URL 里(`session/new` 成功后 `history.replaceState`),不是因为桥接进程在跟踪会话。
- **非回环的网络暴露和 TLS。** 桥接进程写死只绑 `127.0.0.1`,用明文 `http://`/`ws://`。回环流量从不离开本机自己的内核网络栈,所以 TLS 的传输保密性对这个默认场景没有意义;以后如果哪个阶段真要支持绑定别的地址,那时候 TLS 才是必须的,不是现在补。这一版没有开关能改绑定地址。
- **具体前端框架或构建工具的选型。** 调研门自己已经明确把这个留给实施计划;这份设计只钉死合同(TypeScript、一个真正的 ACP v1 客户端实现、构建产物在编译期嵌入桥接二进制,让最终产物还是一个不依赖运行时 npm/node 的自包含单一二进制),不钉死用哪个库。
- **在桥接进程里复用 `internal/client/acp`。** 那个包是给 Go 终端渲染器解析和归约 ACP JSON-RPC 用的;桥接进程什么都不解析。把它导进桥接进程只会是死重量,还会诱使 Go 侧的协议逻辑渗进本该只做传输中继的东西里。

## 桥接进程:一个哑巴中继,不是第二个客户端

`cmd/acp-web-bridge` 照搬 `cmd/acp-client` 自己的子进程生命周期形状——`-agent`(必填)、`-cwd`(必填)、`--` 之后的内容原样转发成 agent 自己的 argv、固定的清理顺序(先关子进程 stdin,再等它退出)——因为正确地拉起并回收一个 ACP agent 子进程,跟用哪种传输方式渲染它的输出没有关系,本项目不会把一个已经做对过一次的、对正确性敏感的模式再重复实现一遍。新增的是 `-listen <host:port>`(默认 `127.0.0.1:0`,操作系统分配的临时端口),取代原来渲染到 `os.Stdin`/`os.Stdout` 的部分。

中继本身不解析 JSON,不检查方法名——这不是偷懒,而是刻意的:ACP v1 本身在被桥接的这条管道两端都已经是一个双工、自描述的 JSON-RPC 流,中继完全不需要理解它。这跟调研门里读到的 Codex 自己 `app-server` 在 stdio/websocket/unix 三种传输之间复用同一套消息 schema,是同一个思路。既有的边界已经把强制执行的活干了:`och -acp` 自己的编解码器已经会对超大的入站行 fail-closed(`maxFrameBytes = 1 MiB`,直接终止 `Serve`),它自己的投影器也已经把每一条出站帧限制在同一个上限内——桥接进程只需要把自己 WebSocket 服务器的最大消息大小设得比 1 MiB 宽松一点(留余量,不是一个新的独立限制),不需要重新实现或重复 `och -acp` 自己的裁剪逻辑。重连是"重新接线",不是"重启":活跃 WebSocket 连接断开(标签页关闭、刷新、网络中断)后来了一个新连接,桥接进程只是把两个搬运字节的 goroutine 重新指向新连接,子进程本身从不重启、也不会被告知——从它的角度看,自己的 stdin 只是短暂没有写入者,而 `och -acp` 本来就正确处理这种情况,因为一个慢一点或者在思考的客户端本就正常。

## 浏览器防护:Origin 白名单加每次启动的令牌

浏览器给本项目的威胁模型引入了一类此前从未命名过的、真正新的不受信输入:操作者自己机器上另一个标签页里的任意网页内容,它可以尝试对任何它能猜到或扫描到的 `ws://127.0.0.1:PORT` 发起 WebSocket 连接,不管这个端口实际服务的是不是操作者真正的 UI。只绑定回环地址**防不住**这个——恶意页面自己的 JavaScript 跑在同一台机器上,能够到任何回环端口。每一次 WebSocket 升级请求都要在握手完成前过两道独立的检查:(1)**Origin 白名单**——如果升级请求带了 `Origin` 头,必须和桥接进程自己服务的 origin(`http://127.0.0.1:<port>`)完全一致,否则用 `403` 拒绝;完全没带 `Origin` 头的请求(非浏览器客户端,或者恰好省略了这个头的同源请求)不会仅凭这一条被拒绝——下面的令牌检查照样要过。(2)**每次启动生成的令牌**——启动时生成一个随机令牌,连同完整的就绪 URL(`http://127.0.0.1:<port>/?token=<token>`)一起打印到 stderr,这跟本项目 exec 沙箱自己那个"记录下来、操作者可见"的逃生舱先例是一致的;被服务的页面自己的脚本从 URL 里读出令牌,作为 WebSocket 查询参数(`/ws?token=...`)带上,因为浏览器 JavaScript 没法给 WebSocket 握手加自定义头。桥接进程用常数时间比较,任何不匹配(包括缺失)都拒绝升级。两道检查都是必须的、相互独立的,谁都不能替代谁。

## 实时轨迹数据:浏览器实际能拿到什么、能近似出什么

浏览器自己的 ACP 客户端实现拿到的,和今天任何一个 ACP v1 客户端拿到的完全一样——不多也不少,`acp-v1.md` 里"Never projected on ACP"那份清单本来就不发给任何客户端的东西,这里也不会多发。也就是说,DeepSeek Harness 的设计启发出来的那个记录检查器,这一版能展示:工具名和 kind、`rawInput`、完成/失败的内容、以及 pending/in_progress/completed/failed 状态。这一版展示不了:token 计数、服务商上报的延迟、`finishReason`,或者首字延迟/解码耗时的拆分——这些字段今天根本不会到达任何 ACP 客户端,不管是不是浏览器。**一个粗略的耗时视图仍然是诚实且可得的**,这份设计把它算作在这一版范围内,恰恰是因为它不需要任何协议改动:浏览器给打开一个 Turn 的 `user_message_chunk`(或者它调用 `session/prompt` 的那一刻)和结束这个 Turn 的最后一条通知或 RPC 响应,各打上一个本地接收时间戳,单从这些本地观测到的时间戳就能推出每个 Turn、每张工具卡片的墙钟时长。这会向操作者披露清楚:这是一个本地的、近似的测量值(会受渲染和事件循环抖动影响),绝不会被标注或呈现成服务商上报的延迟——"客户端自己观测到的事实"和"服务商上报的事实"之间的区别必须保持可见。

## 前端合同(具体库留给实施计划)

TypeScript,编译成静态资源;是一个真正的 ACP v1 客户端,独立实现 `initialize`、`session/new`/`session/load`、`session/prompt`、`session/request_permission` 处理、`session/cancel`,对齐 `acp-v1.md` 和 `internal/client/acp` 已经满足的同一份 wire 合同——这是真正的新客户端协议代码,不是对 Go 侧任何东西的复用,必须针对真实合同去验证,不能因为 Go 已经有一份实现就想当然认为它是对的。按 Turn 分组的台账靠客户端自己知道什么时候调用了 `session/prompt`(实时)或者 `user_message_chunk` 边界(回放)来分组,不需要新字段。选中一条记录打开一个详情视图,展示 `rawInput`/内容/状态/上面那个本地耗时近似值。**权限请求接管输入框的位置,而不是弹模态框**,并且内联展示关联的工具调用详情——这是本文档现在就钉死、不留到以后的一个交互设计决定,因为它跟设计里别的部分没有技术依赖,而设计阶段正是把一个原本没有天然归属者的 UI 决定定下来的合适时机。构建产物在编译期通过 Go 的 `embed.FS` 嵌入 `cmd/acp-web-bridge` 二进制,让最终产物和本项目发布的每一个其他二进制一样,是一个不依赖运行时 Node.js 的自包含单一二进制。

## 验证与验收

见英文版 §7:桥接中继测试(真实子进程加真实 WebSocket 连接,断言双向逐字节的行转帧、帧转行);重连测试(第一个连接断开、第二个连接上来,断言底层子进程没被重启);Origin 和令牌测试(匹配放行、不匹配或缺失一律 `403`、没带 Origin 但令牌对的情况放行);一次真实互操作性证明,标准跟 `TestInteropRealAgentCompletesAnApprovedWriteFile` 一样——用真实的 `och` 二进制、真实的 `cmd/acp-web-bridge` 二进制、真实的 WebSocket 客户端跑完一个完整 Turn(含交互式权限批准);**前端也需要一份同等证据标准的真实端到端证明,不能因为技术栈对本项目是新的就降低门槛**,具体工具留给实施计划,但必须是真实端到端跑通,不能用组件级单测代替。Origin/令牌检查各自的变异测试。Go 侧 `go vet`、`gofmt`、`CGO_ENABLED=0 go build ./...`、`go test -race ./... -count=1`;前端工具链自己对应的静态检查/构建/测试命令,写在实施计划里。

## 风险

详见英文版 §8:恶意标签页尝试连桥接进程的回环端口——靠 Origin 白名单挡在握手完成之前。共享主机上另一个本地账号/进程够到回环端口但从没见过操作者的浏览器——靠独立于 Origin 之外的每次启动令牌挡住。浏览器独立实现的 TypeScript ACP 客户端跟真实 wire 合同产生偏差,因为这是全新代码、不是复用 Go 实现——靠一份针对真实 `och -acp` 二进制的、跟 Go 客户端同等标准的真实端到端互操作性证明来兜底。操作者把本地的、基于接收时间的耗时近似值误认成服务商上报的延迟——前端合同要求这个区别必须保持可见标注。第二个标签页悄悄接管活跃连接,让忘了还开着第一个标签页的操作者困惑——这是这一版明确、刻意的行为,不是缺陷。往会话列表/恢复/删除、转录导出接入、更丰富的时间轴总览方向蔓延——§(范围之外)里每一条都写清楚了理由,下一步的实施计划会像本项目历史上每一份计划一样把任务边界钉死。
