# Exec CPU 配额设计（中文摘要）

**状态：** 已接受（2026-08-31）；本文是与英文规范同步的中文摘要，不是逐字翻译。两者若有分歧，以英文 [2026-08-31-exec-cpu-quota-design.md](2026-08-31-exec-cpu-quota-design.md) 为准。

调研门发现没有一个参考项目对生成的命令做 CPU 配额，一开始还得出"macOS 上找不到任何可用的外部强制机制"的结论——但调研门自己在 2026-08-31 的更正说明里撤回了这个结论，因为发现本项目自己已有的代码（`sandbox_darwin.go` 的 `beginRlimitBracket`）早就解决了这一类问题的通用形态（把父进程自己的 rlimit 围在 `Start()` 调用前后，因为 Go 的 `os/exec` 对一个任意子进程没有 fork-exec 之间的钩子）。这份设计给 `internal/harness/adapters/localexec` 在它今天已经在沙箱化的两个平台上都加上 CPU 配额，用两套真正不同的内核机制统一到同一个策略意图上。

## 核心决策（六条）

1. **这一轮只做 CPU 配额。磁盘 IO 配额（`io.max`）和文件描述符上限（`RLIMIT_NOFILE`）都明确推迟**（英文版 §2 有各自独立的理由），不是为了"一次性把 `SECURITY.md` 那句话补完"而硬凑。
2. **一个策略意图，两套机制。** 两个平台都把一次生成的命令限制在大致一个 CPU 核的聚合工作量以内——Linux 用带宽比例（`cpu.max`，一个速率），macOS 用累计 CPU 秒数上限（`RLIMIT_CPU`），设成跟本项目自己已有的 `DefaultExecTimeout`（30 秒）完全一致。单位不一样是因为内核原语本身不一样；但意图是一致的——不管是一个核心一直转到超过它的墙钟预算，还是分散跑到好几个核上，只要用掉超过一个核的 CPU 就会被限流或终止，抢在它能拖垮跑这个 harness 自己进程、以及其他并发工具调用的宿主机之前。
3. **Linux 只需要给已有的 cgroup 多写一个 controller，不需要新的监控。** `cpu.max` 是内核强制的限流，不杀进程，也没有类似 `memory.max` 那种可以监视的违规通知文件。新增一个纯诊断性质的 `CommandResult.Throttled` 字段（绝不是一个新的"被杀原因"），跑完之后不管怎么结束的都从 `cpu.stat` 的 `nr_throttled` 里读一次填进去。
4. **macOS 延伸现有的 rlimit 围栏技术，加上 `RLIMIT_CPU`，设成在硬限制之前先触发——软硬上限的形状照搬内存自己 `memory.high`/`memory.max` 的模式**——刻意留一个 1 秒的间隔（软 30 秒、硬 31 秒），目的是区分信号来源，不是给宽限期：一个被 `SIGXCPU`（软限制信号）终止的进程，可以比较有把握地归因到这个配额；一个前面没观察到 `SIGXCPU` 的裸 `SIGKILL`，不会被自动当成是这个配额干的。
5. **`Enforcement` 加一个 `CPU` 字段，跟别的每个效果一样按平台分别报告**——Linux 和 macOS 都是 `EnforcementFull`（内核限流/内核杀掉，都很精确），比内存在 macOS 上的 `EnforcementPartial` 评级更高（内存不精确是因为 `RLIMIT_AS` 限的是地址空间而不是常驻内存；`RLIMIT_CPU` 限的东西本身没有这种不精确，唯一的不精确在于本项目事后把一次终止归因到这个配额上这件事，单独在英文版 §6 里说清楚，不折算进强制等级里）。
6. **Windows 不受影响。** 它本来就在整体沙箱层面 fail-closed（上一轮的决定），这份设计在那边什么都不加，也不重新讨论那个决定。

## 范围之外（这次明确不做，不是漏做）

**磁盘 IO 配额（`io.max`）**：调研门发现它限的是*速率*，不是*总共占用的磁盘空间*——解决不了 `SECURITY.md`"磁盘"这个措辞最自然让人以为的那个"工作区被写满"问题，而且它自己的块设备 major:minor 解析问题，六个参考项目里没有一个有先例。总磁盘空间上限（写入总字节数，或者文件系统级配额）是一个比 `io.max` 能解决的问题更难、更不一样的问题，这次也不做设计。

**文件描述符上限（`RLIMIT_NOFILE`）**：在 macOS 上面临着跟 CPU 配额一模一样的架构约束（Go 的 `os/exec` 对一个任意子进程没有 fork-exec 之间的钩子），但在 Linux 上没有 cgroup v2 controller 能顶上——`pids.max` 限的是进程*数量*，不是打开的文件描述符数。这需要一次独立的机制调研，不能想当然套用这次的答案。

**Windows**：本来就整体排除在沙箱之外（上一轮决定），维持不变，不重新讨论。

**一个可配置的 CPU 配额开关**：跟本项目自己已有的先例一致（`DefaultMemoryHighBytes`/`DefaultMemoryHeadroomBytes` 是包级常量，不是 `composition.Config` 字段），CPU 上限这次也是固定的默认值。要不要做成可配置是一个更小、可以独立拆出来的后续改动，等真有部署需要再说。

## Linux：给现有 cgroup 加一个 `cpu.max`

在跟 `memory.high`/`memory.max` 同一个子 cgroup 里，紧接着内存那几次写操作之后，多写一次 `cpu.max`（`"100000 100000"`——100ms 周期内给满 100ms，也就是整整一个核），复用同一套 `cgroup.subtree_control` 委派流程（`+memory` 变成 `+memory +cpu`）。单线程命令永远不会被这条限制碰到；一个往多个核上铺开的命令（并行构建、fork 炸弹、故意起的 CPU 密集型任务）会被限制在大致一个核的聚合调度时间以内——这正是这份设计要防的"拖垮宿主机"风险。

`cpu` controller 写失败（没被委派、宿主机还在用 cgroup v1 等等）不会拖累已经成功的 `memory` 写——cgroup 不会被拆掉，内存配额继续生效，`enforcement.CPU` 独立报告成 `EnforcementNone`，跟"一个 `Runner` 不能对自己实际上没约束住的效果谎称 full"这条本项目自己已有的原则一致，只是把它落到了按 controller 而不是按整个 cgroup 的粒度上。

## macOS：给现有 rlimit 围栏技术加上 `RLIMIT_CPU`

沿用 `beginRlimitBracket` 现成的形状——锁一个互斥锁、调低自己进程的限制、返回一个恢复原值的闭包——套在同一个已经在给 `RLIMIT_AS` 做围栏的 `cmd.Start()` 调用上，加第二个 rlimit：软限制 30 秒（正好等于 `application.DefaultExecTimeout`），硬限制 31 秒。之所以留这 1 秒间隔，是为了让触发 `SIGXCPU`（软限制信号）的终止能比较有把握地归因到这个配额，而不是简单为了给宽限期。

今天的 `Run` 从不检查退出信号是什么——当 `done` 这个 select 分支先触发时，需要新增一段逻辑：检查 `*exec.ExitError` 底下的 `syscall.WaitStatus` 是否 `Signaled()` 且信号是 `SIGXCPU`，或者是 `SIGKILL` 但没有其他分支能解释——命中就设置 `ResourceLimited = true`，跟 Linux 内存路径已经在用的是同一个字段，让两个平台对"这个命令因为超出资源边界被杀"这件事有一个统一的字段，不管具体是哪个资源、哪套机制。

macOS 上 `enforcement.CPU = EnforcementFull`：内核确实不会让一个进程超过 `RLIMIT_CPU` 的硬限制，而且是无条件生效的，跟 Seatbelt 自己可不可用没关系——跟 `RLIMIT_AS` 给内存提供的那种无条件生效的性质是一样的。真正需要说清楚的顾虑范围更窄，单独披露（不折算进强制等级）：把一次终止归因到 `ResourceLimited` 靠的是信号检查，在一个真正罕见的场景下（进程忽略了 `SIGXCPU`，恰好同一个窄窗口里又有别的什么东西单独给它发了 `SIGKILL`）可能会把一次无关的杀掉错误地归到这个配额头上——有问题的只是极端情况下的*标签*，不是这个上限本身的正确性。

## `Enforcement` 与 `SECURITY.md`

`Enforcement` 结构体新增一个 `CPU EnforcementLevel` 字段。`SECURITY.md`"未强制执行"里"任何平台都没有 CPU 或磁盘 IO 配额"这句话，在实现的时候被精确拆开：CPU 那一半挪进"已强制执行"，精确写明它限制的是什么（Linux 和 macOS 上都是大致一个核的聚合工作量）和上面那条信号归因的顾虑；磁盘 IO 那一半留在"未强制执行"里，重新措辞说清楚（按这份调研门自己的发现）即使以后真做了这个机制，它顶多也只是限流速率，解决不了磁盘空间被占满的问题——不让未来的读者以为"磁盘 IO 配额"当初就打算解决磁盘空间耗尽这件事。

## 风险

详见英文版 §7：一个合法的、CPU 密集但单线程的工具调用（跑一个大测试套件、一次慢编译）被误伤限流或杀掉的风险——不存在，因为这两个平台的上限都是刻意选在"聚合、跨核使用"这个维度上，单线程工作不管跑多久都够不到这条线（时长本身已经由现有的墙钟超时单独限制）。macOS 信号归因误判的风险——已经明说是标签层面的、罕见的边界情况，不是上限本身的正确性问题。`cpu` controller 在某台 `memory` 可用但 `cpu` 不可用的宿主机上不可用的风险——按 §（Linux 一节）的独立失败设计处理，`composition.Open` 现有的 fail-closed 门禁本来就不看单个 cgroup controller，这次也不会因为 CPU 配额不可用而新增一道门禁。往磁盘 IO 或文件描述符上限方向蔓延的风险——§2 的排除项已经写清楚各自的理由，下一步的实施计划会像本项目历史上每一份计划一样把任务边界钉死。
