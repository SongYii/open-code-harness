# 通俗实现导读与项目文档规范设计

- 状态：已接受
- 日期：2026-09-10
- 范围：所有已实现模块及未来实现切片
- 英文规范真源：[2026-09-10-plain-language-implementation-guide-design.md](2026-09-10-plain-language-implementation-guide-design.md)

## 1. 问题

仓库很擅长保存技术合同、提交号、测试命令、故意破坏测试和未完成项，但不总能用
普通语言讲清开发过程。新模块会诚实记录错误假设和无效测试；一些早期证据只有
提交表、命令输出以及“当时还没做什么”。其中部分历史描述放到今天已经过时。

中文翻译如果只是逐字翻译技术术语，也不会自动变得容易理解。因此项目需要一个
稳定入口，用同一组简单问题解释每个模块。

## 2. 决策

发布一份英文通俗导读和同步的中文阅读版，覆盖 `docs/README.md` 中每一个
`Implemented contract`。每个模块固定回答五个问题：

1. **解决什么问题**；
2. **用户能看到什么**；
3. **真实实现在哪里、怎么工作**；
4. **开发时发现了什么问题、怎么修复**；
5. **现在还缺什么**。

每节必须链接详细实现合同和证据账本。通俗导读不替代设计、计划、合同或证据，
只负责让读者先建立正确的整体认识。

## 3. 历史证据

证据账本是按时间保存的历史记录，不能为了符合今天的状态而重写。若旧账本中的
“尚未实现”今天已经过时，应在顶部增加醒目标记，说明它是某日快照，并指向当前
架构和通俗导读。新账本必须区分“本切片结束时仍缺少”和“项目当前状态”。

## 4. 自动检查

`internal/docsguard` 从权威表读取全部实现合同，并要求中英文导读链接每一个模块，
且每节都具有固定五问。自动检查只能保证结构和覆盖率；文字是否真正易懂仍由评审
判断。

## 5. 写作规则

- 先说实际结果，再说类型和接口；
- 术语先解释意思，再给名字；
- 用一个真实失败例子代替一串接口名；
- 指出真实代码位置，但不要复制 API 手册；
- 明说测试证明了什么，也明说没有证明什么；
- 如实记录错误假设和无效测试；
- 当前状态与历史证据严格分开；
- ACP、MCP、CAS、SSE 等缩写首次出现时必须展开；
- 每个模块应能在不打开详细合同的情况下快速读完。

## 6. 项目实现规范

一个实现切片只有同时具备以下内容才算文档完成：先设计后计划、真实生产代码与
实现合同、可复跑且关联提交的证据、中英文通俗五问、诚实的问题与偏差记录，以及
与历史快照分开的当前限制。

## 7. 非目标与验收

本次不删减技术合同、不重写历史、不声称测试能衡量文字质量，也不改变运行时代码。
所有现有模块具有双语五问、旧状态有醒目标记、根入口可找到导读、docsguard 能阻止
漏写模块或标题，并且全仓测试通过后完成。
