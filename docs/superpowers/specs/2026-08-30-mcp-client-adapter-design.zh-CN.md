# MCP 客户端适配器设计（中文摘要）

**状态：** 已接受（2026-08-30）；本文是与英文规范同步的中文摘要，不是逐字翻译。两者若有分歧，以英文 [2026-08-30-mcp-client-adapter-design.md](2026-08-30-mcp-client-adapter-design.md) 为准。

**审阅问答：** 人类审阅者问了一个直接的问题——如果别的都不依赖它，现在有必要实现吗？答案是：不必要。已实现的合同（Tool runtime、组合根、ACP v1 adapter）今天完全不依赖 MCP 客户端就能正常工作，里程碑顺序里也没有任何一项卡在它上面。这份设计仍然值得现在写——趁调研门的发现还新鲜，把摆放位置、风险分类、审批路由这些问题先钉下来——但这一轮不跟着写实施计划。这跟里程碑 7（TUI 客户端）和 Context Engine 本体现在的状态是同一种做法：已设计（或已接受方向），未承诺实现。`tools.SourceMCP` 在这份设计之后依然是一个"目录里合法但没有适配器"的占位符，直到出现具体的外部工具需求。

## 核心决策（七条，逐一对应调研门留下的开放问题）

1. **采用 `modelcontextprotocol/go-sdk` 作为钉版本依赖，不自己写协议**——这是对 ACP 那边"协议小到值得自己拥有"先例的反转，理由很具体：调研门里三个独立项目（Codex/`rmcp`、Maka/官方 TS SDK、DeepSeek Harness/官方 TS SDK）都选择采用官方 SDK；而且规范本身在 2026-07-28 这一版做了不向后兼容的修订，官方 SDK 内部已经处理了新旧两代协议共存的问题，自己写就得跟着规范的变动反复重做。
2. **只支持 stdio 传输，Streamable HTTP 这次不做**——本地拉起的 MCP 服务器子进程跟本项目 `exec` 工具面对的操作系统级威胁模型是同一回事；远程 HTTP 服务器会带来 OAuth、TLS、Origin 校验这些跟"把外部工具接进现有管线"这个核心目标无关的复杂度，先不解决。
3. **MCP 服务器配置是组合根时刻的静态列表，ACP adapter 现在对 `mcpServers` 的 fail-closed 拒绝保持不变**——跟 `localexec`/`workspacefs` 今天的接线方式一样，是配置项，不是运行时可变的东西。
4. **每一个被发现的 MCP 工具一律分类成 `domain.RiskExec`，绝不新开一个风险维度，也绝不信任工具自己声明的只读/破坏性标注**——规范自己写得很明确：这些标注"必须被当作不可信的，除非来自可信的服务器"。`RiskNetwork`（今天在所有模式下都无条件拒绝）继续留给未来可能的内置联网工具，不挪用给 MCP：MCP 工具在本项目自己的风险语汇里不是"联网"，而是"不可信的外部代码执行"，这正是 `RiskExec` 已经代表的含义。
5. **工具重名靠前缀解决，不改 `Catalog` 本身**——`mcp__<server>__<原始名字>`，直接采用 DeepSeek Harness 的先例；`Catalog` 依然要求全局唯一、依然不可变。
6. **MCP 工具调用的参数完全绕开固定字段的 `toolArgs` 解码和工作区路径校验流程**——`tools.ValidateArgs` 今天已经在 `parseToolArgs` 之前、且与工具来源无关地按 schema 校验过原始参数，这条已经是现成的、不用改的东西；MCP 调用不属于本项目自己的工作区文件系统，所以"是否在工作区内"这个问题对它不适用，一律按 `WorkspaceIn: true` 处理。
7. **审批路由完全不变**：MCP 工具调用走跟 `exec` 今天一模一样的 `Policy.Decide` 表和 `Approver`/`tools.Slot` RPC，不新建一套审批子系统——这是调研门里最扎实的一条交叉证据（Codex 的 MCP 工具审批和自己内置工具建议共用同一个判别键空间）的直接应用。

## 范围之外（这次明确不做，不是漏做）

不写实施计划；不做 Streamable HTTP；不接受 ACP 按会话传的 `mcpServers`；不做 Resources/Prompts；不声明 `sampling`/`elicitation`/`roots` 客户端能力；不做目录热更新（`notifications/tools/list_changed`，目录依然是组合根启动时构建一次、不可变）；协议新旧时代的判断完全交给采用的 SDK，本项目自己不做选择。

## 落地位置

新适配器包 `internal/harness/adapters/mcp`，遵循现有 `adapters/*` 的目录架构规则（只有 `composition` 能导入它，它不能导入任何兄弟 adapter）——这是对 `internal/harness/architecture` 现有依赖边界测试表的一次机械式扩展，不是新机制。子进程复用 `localexec` 现成的操作系统级隔离（Linux 上 bwrap/cgroup v2、macOS 上 Seatbelt/RLIMIT_AS），不新建第二套沙箱机制。发现阶段设了具体的资源边界（每服务器最多 256 个工具、单个工具定义最多 64KiB），超界或发现失败会让 `composition.Open` 直接失败——fail-closed，没有类似 `AllowUnsandboxedExec` 的逃生阀，因为正确的补救方式是修好或删掉那条服务器配置，而不是带着一个已知坏掉的工具悄悄跑起来。

## 风险

主要风险和缓解措施详见英文版 §10：协议新旧时代分裂交给 SDK 吸收；恶意/异常服务器的工具列表用资源边界防护；把所有 MCP 工具统一按 `RiskExec` 处理是刻意选择的保守立场（而不是遗漏）；长生命周期的服务器子进程跟一次性的 `exec` 调用在资源配额跟踪上的差异,留给未来的实施计划去对着 `localexec` 真实 API 解决;没有具体外部工具需求就去实现,本身就是一种风险——这也是这份设计止步于"设计"、不写实施计划的直接原因。

## 2026-09-04 修订

英文正文在 2026-09-04 就地标注了四处修订，以下是摘要。英文版仍然是权威来源；上文各段保留 2026-08-30 当时的原状，未被改写。

**实施已获授权。** 上文"这一轮不跟着写实施计划""直到出现具体的外部工具需求"这两句所描述的前置条件，由项目决策直接解除——不是因为出现了某个具体的外部工具，而是直接决定动手。实施计划现在跟在这份设计之后。

**§3 与 §6 原本互相矛盾。** 上文第 23 行把"不能导入任何兄弟 adapter"和"复用 `localexec` 的沙箱"写在了同一句里，而 `localexec` 正是一个兄弟 adapter——照原文实现会被现有的 `TestForbiddenImport` 当场拦下。修订后的做法是：mcp 适配器**永不**导入 `localexec`，它只拥有一个窄接口（返回已配置但尚未启动的 `*exec.Cmd` 的受限命令工厂），由唯一有权同时导入两者的 `composition` 注入 `localexec` 实现。

**`localexec` 目前没有可复用的 API，需要新建。** 它唯一的执行入口 `Runner.Run` 是跑完即返回的：输出被收进有上限的缓冲区，临时目录和 cgroup 注册都只在这一次调用的作用域内。而 MCP 服务器需要的恰好相反——一个带 stdin/stdout 管道、存活到进程结束的子进程。可复用的零件是齐的（`bwrapArgv`/`seatbeltCommandArgv` 是纯 argv 变换，cgroup 辅助函数只要一个 pid），所以 `localexec` 会在 `Run` 之外新增一个长生命周期入口，这是实施计划里独立的一项任务，不是接线细节。

**§5 关于重名的论断是错的，而且这个缺口能被不可信服务器触达。** 前缀并非单射：`tools.validateSpec` 允许名字里出现 `__`，因此服务器 `a` 的工具 `b__c` 与服务器 `a__b` 的工具 `c` 会得到同一个限定名 `mcp__a__b__c`——两个服务器名并不相同。原始工具名来自被本设计自身威胁模型视为不可信的服务器，而 `NewCatalog` 在 `composition.Open` 处 fail-closed，所以一个恶意服务器可以挑一个与**另一台**服务器的工具相撞的名字，让整个 harness 起不来。修订后的规则：拼接前先把两部分都清洗成 **`[a-zA-Z0-9-]`**——只保留 ASCII 字母、数字和连字符，**不含下划线**。下划线被专门保留作分隔符，把它排除在部件字母表之外，正是让拼接具备单射性的全部机制。限定名上限 64 字节，超出则截断并追加一个稳定的 8 位十六进制 FNV-1a 后缀。清洗本身是有损的（`a/b` 与 `a.b` 都会变成 `a-b`），所以**被清洗改动过**的部件会再带上一个针对其原始字符串的 8 位十六进制 FNV-1a 后缀；本来就合法的名字原样通过，这样常见工具名对模型仍然可读，而不是无条件全部哈希。

**同日第二次修订，由实现发现。** 这一段最初写的规则是「清洗成 `[a-zA-Z0-9_-]` 并折叠下划线连续段，从而把分隔符从两部分中移除」——这是错的：那个字母表**保留**了分隔符，因此 `a` + `b__c` 与 `a__b` + `c` 仍然会得到同一个名字。Task 1 的单射性测试在按原规则实现时直接失败，而把字母表改回原写法的变异会让该测试重新变红。上面是修正后的规则。Kimi Code 的约定仍然是「上限加后缀」这套机制的来源，但它的字母表不是，因为它的分隔符是 `__` 而非单个被保留的字符。

**依赖数量的说法也过期了，而且真实代价不止一个模块。** 上文所依据的"第二个非测试依赖"在 2026-08-30 是准确的，但网页轨迹 UI 那一片之后加入了 `github.com/coder/websocket`，现在非测试依赖已有四个。更重要的是，导入 SDK 的 `mcp` 包在生产路径上会传递性地引入六个模块，其中 `golang.org/x/oauth2` 经由 `mcp` → `auth` → `oauthex` 到达——即便本设计只做 stdio、完全不触及任何 OAuth 代码路径，也无法避开。实施该设计的那一片必须据实重写 `SECURITY.md` 的依赖声明。

## 2026-09-05 修订：schema 校验降级，不丢弃工具

英文正文 §5 就地标注了这条修订，以下是摘要，英文版为准。

**问题。** Task 1 实测发现，本项目的 `tools.compileSchema` 是为自己那四个内置工具量身定做的：关键字白名单只有 12 项且递归生效，类型只认四种。真实 MCP 工具说明书里极常见的写法几乎全被拒绝——给参数加 `description`（几乎每个工具都有）、`$schema`、`title`、`"type":"number"`、`"type":"boolean"`、`anyOf`、`default`，以及没有写 `additionalProperties:false` 的对象说明书。按原先「编译不过就丢掉这一个工具」的规则，一台健康的服务器会被成功发现、每个工具都被丢掉，程序照常启动却一个工具都不可用——**失败得悄无声息，而且长得跟成功一模一样**。

**参考项目无一这样做。** Codex 把 `input_schema` 存成无类型的 `serde_json::Value`；Kimi Code 的全部校验就是「它是不是一个 JSON 对象」；DeepSeek Harness 的输入说明书原样透传，对它确实检查的输出格式则明确写着「看不懂的 MCP 词汇退化为任意 JSON 值」；Maka 用的是符合标准的 Ajv。四个项目，没有一个用自研白名单去卡外部说明书。

**修订后的规则：降级，绝不丢弃。** 对 `tools.SourceMCP` 的工具：`InputSchema` **原样**保存服务器的说明书，因为同一个字段正是 `openaicompat/model.go:346` 发给模型的内容，换成宽松的替身会让模型看不到真实参数、工具直接不可用；注册环节只要求它是一个有界的 JSON 对象，不要求可编译；每次调用时先尝试编译，能编译就按内置工具同样的严格程度校验参数，不能编译就退化为「参数必须是一个 JSON 对象」。工具在任何一种情况下都保持可用。降级会被**记录**而不是静默发生。

**这处修订窄幅改动了本设计头部「不得修改的已实现契约」清单中的 `tools`。** 全仓库只有两个 `compileSchema` 调用点，分支以 `spec.Source` 为键，内置路径必须由测试证明逐字节不变。备选方案「直接放宽 `compileSchema`」会连带放松四个内置工具的校验，而它们的 `additionalProperties:false` 正是为了挡住模型臆造的键。

**为什么对 MCP 可以松、对内置不行。** 内置工具的说明书由本项目编写、活也由本项目的代码干，严格校验保护的是自己的文件系统和执行路径；MCP 工具的说明书由服务器编写、活也由服务器干，拒绝错误参数本来就是它自己的责任。真正保护本 harness 的三层完全没变，且与说明书是否规范无关：每个 MCP 工具一律 `RiskExec`（宽松模式下必须审批，严格模式下直接拒绝），服务器子进程跑在 `localexec` 的沙箱里。
