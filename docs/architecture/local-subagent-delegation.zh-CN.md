# 本地子代理委派：通俗说明

- 状态：已实现合同
- 实现日期：2026-09-12
- 英文真源：[local-subagent-delegation.md](local-subagent-delegation.md)
- 实现证据：[local-subagent-delegation-evidence.md](local-subagent-delegation-evidence.md)

## 它解决什么问题

主模型需要查很多文件时，可以把一个明确的小任务交给“新开的一张工作台”。子代理没有
主对话的长历史，只拿到任务、系统规则和当前仓库的 `AGENTS.md`，因此探索内容不会继续
挤占主对话。

它不是联网的多 Agent 系统，也不是后台蜂群；就是本进程内新建一个真实 Session，再跑
一次普通 Turn。

## 怎么开启

默认关闭，因此不会多出 Tool Schema，也不会影响原来的模型缓存键。启动 `och` 时加
`-subagents` 才会出现 `delegate_task`。超时默认两分钟，可用
`-subagent-timeout` 设置为 5 秒到 10 分钟。

主模型会等子任务结束，然后拿到“子 Session ID + 最终回答”。Session ID 方便事后查账，
返回正文仍受原有 64 KiB 工具结果上限保护。

## 真实实现重点

子代理不是一段临时字符串。系统真的创建一条新的 `session.created`，并记住它由哪个
父 Session、父 Turn、工具 Item 和 Call ID 创建。重启后重放事件，父子关系仍在；旧事件
没有这个新字段，照常读取。

子 Session 走同一套模型、Context Engine、SQLite、指令发现和 Trace，不复制父对话。
所以它既是“干净上下文”，又没有绕过现有基础设施。

## 为什么它不能偷偷改文件

有两道门：发给子模型的工具列表里只有 `read_file` 和 `list_dir`；即使模型无视列表，
硬发 `write_file`、`edit_file`、`exec`、MCP 或再次委派，执行入口还会拒绝。测试故意
伪造了隐藏的写调用，文件没有变化。

子代理读过的文件版本也只记在自己的 Session 下，不能替主代理取得写入资格。

## 取消和失败怎么处理

主请求取消会一起取消子 Turn，并分别写下正常的中断事实；超时只给主模型固定的
`subagent_timeout`，其他子任务错误给 `subagent_failed`。Provider 的原始报错不会塞回
主对话或事件库。没有后台任务遗留。

父、子是两条独立事件流，不假装能跨流原子提交。只要子 Session 已创建，它的来源就
可以审计；父工具结果遇到“提交结果未知”时，现有执行去重也不会再跑第二个孩子。

## 开发中解决的难点

- 只隐藏写工具不够，恶意或异常 Provider 仍可伪造调用，所以又在执行入口加了独立白名单。
- 父子事件无法做一个 SQLite 跨流事务，于是把“子 Session 创建成功”定义为明确发布边界，
  并用完整父调用坐标保留可恢复关系。
- 子模型失败不能把密钥形状的原始错误带回主对话，因此所有失败归一成固定短码，并用
  canary 测试搜索持久事件。
- 截取多字节回答时可能切断一个 UTF-8 字符；结果上限现在会退到完整字符边界。
- 第一版让“模型看不见写工具”和“执行入口拒绝写工具”共用一个白名单函数，一次误改
  可能同时放宽两道门。变异测试发现后，两处改成真正独立的封闭判断。

## 还没有什么

没有后台子代理、等待/发消息/中断工具、父历史复制、继续同一个孩子、角色或模型选择、
写入审批、远程 Agent、蜂群调度和崩溃后自动续跑。这一版故意只做深度一层的同步只读任务。
